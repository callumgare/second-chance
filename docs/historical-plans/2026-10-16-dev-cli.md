# Replace the dev shell scripts with one Swift CLI (`sc`)

> Frozen plan, implemented 2026-10-16. [docs/dev-cli.md](../dev-cli.md) describes
> `sc` as it is; this records what was intended and why. Where the
> implementation departed from the plan:
>
> - **Log mirroring.** The plan had the CLI pass the app `--mirror-logs` when
>   piped. That flag mirrors logs to a file in Downloads, not stderr; the app
>   gained `SECOND_CHANCE_LOG_STDERR` instead, which `sc wrapp build` sets.
> - **`wrapp run` with an existing wrapp doesn't build the app.** Launching a
>   wrapp as it is doesn't need it; only `--refresh-wrapp template|full` (or a
>   missing wrapp) does.
> - **The `l` key** is read by sc's own small reader, not Noora's
>   `KeyStrokeListener`, which turns off ISIG and exits 0 on Ctrl-C.
> - **Tables** all use Noora's updating table: its static
>   `table(_:renderer:)` ignores the renderer it is given, which tore the live
>   region.
> - **The unit test bar's label** is a separate status line: Noora's
>   progress-bar step can't change its message while it runs.
> - **Collapsed steps** don't show elapsed time (Noora's collapsible step
>   takes its success message up front); progress steps do.
> - **`--debug no-cursor-lock`** was added for the `SECOND_CHANCE_CURSOR_LOCK`
>   switch that landed while this was being built, and a value may contain
>   commas (`wine=+seh,+d3d9`).
> - **The unit denylist** also excludes `ExiftoolServiceIntegrationTests`,
>   which the old allowlist had left out too.

## Context
The top-level dev scripts (`build.sh`, `run.sh`, `build-game.sh`, `update-game.sh`,
`run-tests.sh`, `prepare-release.sh`, `reset-tcc.sh`, `in-gui-session.sh` and
`lib/game-info.sh`) have a number of problems:

- **Overlapping flags.** `--quiet`/`--raw-logs` are repeated in three scripts, there
  are three spellings of "launch" (`--launch`/`--launch-game`/`--launch-args`),
  and `--rebuild` differs from `--rebuild-game`.
- **Scripts calling scripts.** `run.sh` calls `build-game.sh` and `update-game.sh`.
- **Awk parsing.** `lib/game-info.sh` parses `GameInfoProvider.swift` with awk.
- **Sharp edges:**
  - Run with no arguments, `run-tests.sh` runs the hours-long integration suite.
  - Launch args are split on spaces.
  - `update-game.sh` only works from the repo root.
  - `run.sh` uses a stale app because it only builds when the app is missing.
  - The unit test allowlist silently drops new suites.

The goal is one Swift CLI with a freshly designed API built from a list of behaviours,
not from the old flags.

## Requirements (behaviours, confirmed with the user)
1. **Build the app.** Debug build of Second Chance.app. Every xcodebuild call
   builds all architectures (the `ONLY_ACTIVE_ARCH=NO` invariant). Build/test
   tool output can be shown formatted, raw, or not at all.
2. **Run the app.** Its logs reach the terminal. Controllable behaviours:
   - showing the log window
   - skipping the game installer during a wrapp build
   - starting from an empty Wine prefix cache
3. **Build a wrapp, headless, from a game's local disk images.**
   - The game is chosen by its slug, resolved against `GameInfoProvider`.
   - The installers dir and output dir can be overridden.
   - An unknown slug or a missing ISO says what *is* available.
   - Controllable behaviours:
     - what happens when an official patch fails (continue or cancel)
     - whether a failed silent install may fall back to an interactive one
     - skipping the installer
   - Disk is the only source for now. The API must take other sources
     (Her installer, Steam) later without reshaping.
4. **Refresh an existing wrapp's template binary** without reinstalling the game.
5. **Launch a wrapp.** Its logs reach the terminal, arbitrary args are passed through
   intact, and Wine can be run inside its prefix (regedit, a shell, etc.).
   Debug behaviours are chosen through one option-selection mechanism:
   - log window
   - debug-settings dialog
   - Wine debug channels
   - keep in Dock
   - native fullscreen off
   - Wine's desktop not pre-started
   - startup diagnostics off, or a different slow-start threshold
6. **Run tests.**
   - **Unit tests** on their own, as the fast loop.
   - **All tests** (unit + integration) is the default when no suite is named.
   - **Integration tests** cover all games or a chosen list, can reuse prebuilt
     wrapps, and fail rather than skip when installers are missing.
   - **Shared behaviour:**
     - Either rebuild or reuse the existing build.
     - Write an HTML report, opened or not.
     - The exit code reflects the result.
7. **Prepare a release.**
   - **Preflight:** a clean tree, a warning when not on `main`, and warnings when
     the hook is missing or commits are non-conventional.
   - **Version:** computed by cog or forced. Refuse when the tag already exists
     or there are no releasable commits.
   - **Project:** rewrite the version in the SecondChance and WrappTemplate targets
     only. The build number is the commit count.
   - **Changelog:** release notes, plus a new section added to the top of the
     changelog.
   - **Build:** run the unit tests, then do a Release build and package a `ditto`
     zip. Print the architectures, the sha256 and a notarisation warning.
   - **Stop short of publishing:** print the publish commands instead of running them.
   - **Modes:** dry run, notes only, skip tests.
8. **One-time repo setup.** Install the commit-msg hook and check the required
   tools (xcbeautify, xchtmlreport, cog), with install hints.
9. **Clear caches/build outputs** (the Wine prefix cache, among others).
10. **GUI session and remote.**
    - Over SSH, commands that need a GUI run in the console user's Aqua session
      automatically. Output streams back, and the job dies with the session.
    - A locked screen fails up front any command that has to see or click the
      screen. Commands that only need to open windows warn and carry on.
    - Any command can be run on a remote Mac. The source is synced first, and
      test reports are copied back.
11. **Works from any directory.**

Dropped: the TCC reset command and the game-listing command. Out of scope: the
Xcode build-phase scripts in `WrappTemplate/` and `.local/`.

## API design

Noun first, then verb. There are two things you build and run (`app` and `wrapp`),
and everything else is a single-purpose command.

**Two kinds of build, never an unqualified "build" option.**
- The *app build* is everything xcodebuild produces: Second Chance.app, the
  WrappTemplate.app inside it, WrappPuppeteer and the test bundle. A command that
  needs these runs an incremental app build first. `--skip-app-build` (only on
  those commands) uses whatever is in DerivedData instead, and fails if it's empty.
- A *wrapp build* installs a game into a wrapp. Commands that use an existing
  wrapp take a single option, `--refresh-wrapp <method>`, to say how to bring it up
  to date first:
  - `skip`: use it as it is (matching `--skip-app-build`).
  - `template`: put the app build's WrappTemplate binary and dylib into the
    existing wrapp and re-sign it (what `wrapp update` does).
  - `full`: a full wrapp build that replaces it (what `wrapp build` does).

  The defaults differ by command. `wrapp run` defaults to `skip`, and does a full
  wrapp build anyway if no wrapp exists. `test integration` defaults to `full`,
  because the wrapp build is what it tests.

Which commands take which:

| Command | App build | `--skip-app-build` | Wrapp options |
| --- | --- | --- | --- |
| `app build` | yes (that's the command) | — | — |
| `app run` | yes | ✓ | — |
| `wrapp build` | yes | ✓ | — (always a full wrapp build) |
| `wrapp update` | yes (needs a fresh template) | ✓ | — |
| `wrapp run` | yes | ✓ | `--refresh-wrapp` (default `skip`) |
| `wrapp wine` | no | — | — (fails if the wrapp doesn't exist) |
| `test` (all) | yes | ✓ | `--refresh-wrapp` (default `full`) |
| `test unit` | yes | ✓ | — |
| `test integration` | yes | ✓ | `--refresh-wrapp` (default `full`) |
| `release` | its own Release build | — | — |

```
sc [global options] <command>

Global options (all commands)
  --logs collapsed|full|raw         How streamed tool output is shown. This covers xcodebuild,
                                    tests, the headless app and rsync. Default: collapsed in
                                    an interactive terminal, raw when piped/redirected. See
                                    "Output and DX".
  --on <host>[:<path>]              Run this command on a remote Mac (default path: the repo's path under ~)

sc app build                        Build Second Chance.app (Debug)
sc app run [--skip-app-build] [--debug <opt>…] [-- <app args>]
      debug opts: log-window, skip-installer

sc wrapp build <slug> [--skip-app-build] [--from disk] [source options]
                      [--patch-failure continue|cancel] [--debug <opt>…] [--wrapps-dir <dir>]
      Always a full wrapp build; replaces an existing wrapp.
      Interactive: press `l` during the build to launch the wrapp when it finishes.
      disk source options: --installers-dir <dir> (default $INSTALLERS_DIR or installers/)
                           --disk <iso> (repeatable; overrides installers/<slug>/disk-N.iso)
      debug opts: log-window, skip-installer, strict-install
sc wrapp update <slug> [--skip-app-build] [--wrapps-dir <dir>]
      Copy the app build's WrappTemplate binary + debug dylib into the wrapp and re-sign it
sc wrapp run <slug> [--skip-app-build] [--refresh-wrapp skip|template|full] [--debug <opt>…]
                    [--wrapps-dir <dir>] [-- <wrapp args>]
      Default skip: use the existing wrapp, doing a wrapp build only if none exists.
      debug opts: log-window, settings-dialog, wine=<channels>, keep-in-dock,
                  no-native-fullscreen, no-prestart-desktop, no-diagnostics, slow-start=<seconds>
sc wrapp wine <slug> [--wrapps-dir <dir>] [-- <wine args>]
      Run the wrapp's Wine in its prefix (e.g. `-- regedit`, `-- cmd`)

sc test [<slug>…] [--skip-app-build] [--refresh-wrapp …] [--wrapps-dir <dir>]
      No subcommand = all tests: unit, then integration (all games, or the slugs given).
      Takes the integration options, which apply to its integration half.
sc test unit [--skip-app-build]
sc test integration [<slug>…] [--skip-app-build] [--refresh-wrapp full|template|skip] [--wrapps-dir <dir>]
      Default full. template/skip: the CLI refreshes (or not) the existing wrapps itself,
      then runs the suite with TEST_RUNNER_SKIP_BUILD=1 so it only launch-tests them.
      A missing wrapp fails under template/skip rather than being built.
      Shared: --open-report failures|always|never (default failures)

sc release [--version X.Y.Z] [--dry-run | --notes-only] [--skip-tests]
sc setup                            Install the cog commit-msg hook, install fish completions,
                                    and check the required tools
sc clean <target>…                  wine-prefixes | build | wrapps | test-results
sc in-gui-session -- <command…>     Run any command in the logged-in user's GUI session, so it can
                                    open windows even from an SSH shell (combine with --on to do
                                    it on a remote Mac). Already in the GUI session, it just runs.
```

Design points:
- **`--debug` is one repeatable, comma-separable option.** Each command validates its
  own set and lists it in `--help`. `--debug help` prints the list with descriptions.
  Each value maps to the app/wrapp flag or `SECOND_CHANCE_*`/`STRICT_INSTALL` env var
  it stands for. That mapping lives in one table, so a new switch is one row.
- **Sources.** `--from` is an enum with a single case (`disk`) today. Each source
  type owns its options (an ArgumentParser `@OptionGroup`) and its translation to the
  app's `INSTALLATION_SOURCE`/env inputs, through a `WrappSourceOptions` protocol.
  Adding `her-download` or `steam` means adding a case and a conforming type, the
  same shape as the app's `WrappBuildStrategy`.
- **"Launch after build" is not a `wrapp build` flag.** You can decide up front with
  `wrapp run --refresh-wrapp full`, or mid-build by pressing `l` (see "Change your
  mind mid-build"). Either way, the CLI launches the wrapp itself with stdio attached. `LAUNCH_GAME` is not used.
- **Starting from a fresh Wine prefix** is `sc clean wine-prefixes`. The CLI deletes
  `~/Library/Caches/SecondChance/wine-prefix-cache` itself, so the app's
  `--clear-wine-cache` flag isn't needed by the tooling.
- **Log mirroring is automatic.** When stdout isn't a TTY, the CLI passes
  `--mirror-logs`, so piping a run still shows logs.
- **Unit suite = everything minus a denylist** (`DiskInstallIntegrationTests`,
  `ExiftoolServiceTests`) via `-skip-testing:`. A new suite then runs by default
  instead of silently never running. The tool's own Swift tests also run under
  `sc test unit`.
- **Bare `sc test` runs everything.** It's one app build followed by two xcodebuild
  test runs (unit, then integration with its single worker and env), each with its own
  `.xcresult` and one combined report. That way the integration settings never leak
  into the unit run. The exit code is non-zero if either run fails, and integration
  still runs when unit fails. Because this takes hours, AGENTS.md tells agents to
  always name a suite. `release` explicitly runs `test unit`.
- **GUI session.** The commands that need one are `app run`, `wrapp build`,
  `wrapp run`, `wrapp wine`, `test integration` and `in-gui-session`. They check
  `launchctl managername`, and outside Aqua they re-run *themselves* as a one-off
  LaunchAgent under a pty (a port of `in-gui-session.sh`).
- **Locked screen: no override flag.** The check runs only when the screen is locked.
  Each GUI command declares whether it needs to *interact with* the screen or only
  needs a WindowServer connection.
  - Only `test integration` needs to interact: WrappPuppeteer's clicks land on the
    lock screen and its screenshots miss the game. It fails before building
    anything, with a "screen is locked" message.
  - The rest warn and carry on: `app run`, `wrapp build`, `wrapp run`, `wrapp wine`
    and `in-gui-session`. Wine runs fine with the screen locked.
  - This replaces `SKIP_LOCK_CHECK`.
- **Remote.** `--on host[:path]` does the following:
  1. rsyncs the repo, using the excludes from `.local/AGENTS.md` plus the tool's `.build`.
  2. Runs `ssh -t host 'cd path && ./sc <same args without --on>'`.
  3. For test commands, rsyncs `test-results/` back and opens the report locally.

## Libraries and practices (from the review)

Toolchain here: Swift 6.2.4 and Xcode 26.3. The package uses `swift-tools-version: 6.0`
with strict concurrency.

**Adopted:**
- **swift-argument-parser 1.8.x**, Apple's standard, used by SwiftPM and swift-format.
  Version 1.8 needs Swift 6. The features that matter here:
  - `AsyncParsableCommand`.
  - `@OptionGroup` for the shared options (`--skip-app-build`, `--wrapps-dir`,
    `--logs`), so each is defined once.
  - `ExpressibleByArgument` enums for `--refresh-wrapp`, `--from`, `--logs`
    and `--patch-failure`, so `--help` lists the valid values and typos are rejected.
  - `validate()` for cross-option rules.
  - `@Argument(parsing: .postTerminator)` for `-- <args>` pass-through.
  - `defaultSubcommand` for bare `sc test`.
  - Built-in `--generate-completion-script fish`. The project's shell is fish, and `sc setup`
    installs the script into `~/.config/fish/completions/`. One caveat: completion
    generators don't understand custom parsing strategies, so `--` pass-through
    args won't complete.
- **swift-subprocess 1.0** (swiftlang). It shipped with Swift 6.4 and needs Swift
  6.2 and Xcode 26, which this machine has. The features that matter here:
  - Async, streamed stdout/stderr.
  - Environment as `.inherit.updating(…)`.
  - The working directory.
  - `teardownSequence`, so Ctrl-C stops xcodebuild, xcbeautify and the app cleanly.

  It replaces hand-rolled `Foundation.Process` code. Runs that must own the terminal
  use `execv` instead: `app run`, `wrapp run`, `wrapp wine` and `ssh -t`. That way
  the child gets the real TTY and signals directly. The GUI-session pty stays
  `/usr/bin/script`, as today, because Subprocess has no pty support.

- **Noora**, Tuist's terminal design system.
  - **Status.** Actively released (0.57.5 on 8 Oct 2026, several releases a month;
    last commit 14 Oct). It needs macOS 13+.
  - **Dependencies it brings:** Rainbow, swift-log and tuist/path.
  - **Components:** progress, progress-bar and collapsible steps;
    success/warning/error/info alerts; static and updating tables; prompts; text
    styling.
  - **Pinning:** `.upToNextMinor`, because it's 0.x.

  Checking the source turned up two things that affect the design:
  - **Interactivity is detected from stdin, not stdout** (`Terminal.isInteractive()`,
    with `NO_TTY` as an override). Left alone, `./sc … | cat` from a terminal would
    animate into the pipe. So `UI` builds Noora with
    `Noora(terminal: Terminal(isInteractive: <resolved>, isColored: <resolved>))`
    from our own resolution, which is stderr-is-a-TTY plus the `--logs` mode.
    `NO_COLOR` and `CLICOLOR_FORCE` are already honoured.
  - **Only one live component at a time.** The `Renderer` doc says so: "there can
    only be one renderer active at the same time. It's the consumer's responsibility…".
    Every component takes a `renderer:` parameter, though, and `Rendering` is a
    public one-method protocol. That makes a stacked renderer possible (see "Live
    regions" below).

  How Noora is used is described under "Output and DX".

**Considered, not adopted:**

| Library | Why not |
| --- | --- |
| CorvidLabs/swift-cli, TermKit, ConsoleKit, Progress.swift, SwiftyTextTable | Respectively: 2 stars and no releases; a full-screen TUI toolkit that looks stale; tied to Vapor and offers less; and the last two each do only one of the things Noora does. |
| swift-configuration 1.0 | Built for layered service config. Here only a few env vars feed in, and ArgumentParser can read those directly. |
| Rainbow (terminal colours) | Last released in 2021, and too small a need to justify a dependency. |
| swift-log | The app uses it, but a CLI's user-facing output belongs on plain stdout/stderr, not in a logging pipeline. |
| swift-tools-support-core | Deprecated. |

Best practices to follow (from clig.dev and ArgumentParser's guidance):
- **Logic in a library target, thin executable.** `SCKit` holds the commands and
  logic, and the `sc` executable just calls `SC.main()`. Tests import `SCKit` and parse
  real argument arrays with `SC.parseAsRoot([...])`, which covers command validation
  without spawning processes.
- **Streams.** Status and progress go to stderr. Results go to stdout, for example
  `wrapp build` prints the wrapp's path, so `open "$(./sc wrapp build x)"` works.
- **Colour and animation.** Off when stderr isn't a TTY, when `NO_COLOR` is set or
  when `TERM=dumb`. Noora's non-interactive mode handles most of this. `NO_COLOR`
  and `TERM=dumb` are checked to confirm Noora honours them, and if it doesn't, a
  plain theme is passed in.
- **Exit codes.**
  - The child process's code is passed through, as `ExitCode(n)`.
  - Usage errors are 64 (ArgumentParser's default).
  - `CleanExit` is used, never `exit()`.
  - Errors are plain sentences with the fix in them, for example "No wrapp for
    stay-tuned in built-apps/ — run `sc wrapp build stay-tuned`".
- **Ctrl-C.** Children are torn down and temp files and LaunchAgents removed. A
  second Ctrl-C forces the exit. Each command is also safe to re-run after an
  interrupted run (crash-only).
- **Prompts are a convenience, never a requirement.** They only appear when stdin is
  a TTY, and every prompted value also has a flag. Without a TTY, as with `--on`
  without `-t`, the LaunchAgent re-run or CI, the command falls back to the default
  or fails with the flag to pass.
- **Consistent naming.** The same option name means the same thing on every command.
  Nouns come before verbs. Destructive commands (`clean`) say what they deleted, and
  `release` keeps `--dry-run`.
- **Print something within about 100 ms.** Every command prints its first status
  line before its build starts.
- **Few dependencies.** Direct dependencies are two Apple/swiftlang packages plus
  Noora (which brings Rainbow, swift-log and tuist/path), all pinned with
  `.upToNextMinor`.

## Output and DX (Noora)

All terminal output goes through one `UI` type in `SCKit/Support/UI.swift`, which
wraps a `Noora` instance. No command prints directly. That keeps styling consistent
and lets tests swap in a recording UI.

**Streamed logs: `--logs collapsed|full|raw`.** The default depends on where the
output is going:
- **Interactive terminal** (stderr is a TTY, `TERM` isn't `dumb`): defaults to `collapsed`.
- **Anything else** (piped, redirected, CI or an agent capturing output): defaults
  to `raw`. That gives the unaltered tool output, which is the most useful form for
  `grep`, log files and reading after the fact.
- **The decision is made once, by the process you invoked.** The GUI-session re-run
  runs under a pty, and `--on` uses `ssh -t`, so both would otherwise look
  interactive even when the original caller was piping. The original process resolves
  the default and forwards it as an explicit `--logs <mode>`.

The modes:
- **`collapsed`** uses Noora's **collapsible step**. While a step runs, it
  shows the last few xcbeautify-formatted lines under the step's title. On success it
  collapses to a single ✓ line with the elapsed time, so the scrollback holds one line
  per step.
- On failure, the step expands. It shows the error and warning lines xcbeautify
  found, followed by the path to the full log.
- **`full`** prints every formatted line (today's default). **`raw`** prints
  unformatted xcodebuild output (today's `--raw-logs`). In those modes, the steps
  show as plain start and end lines.
- The full raw log of every step is always written to `DerivedData/sc-logs/<time>-<step>.log`,
  whatever the mode, so collapsing never loses information.
- This replaces today's `--quiet`. Collapsed output is already one line per step.

**Steps by command** (collapsible unless noted):

| Command | Steps |
| --- | --- |
| `app build` | "Build Second Chance" |
| `wrapp build` | "Build Second Chance", then a **progress step** "Build wrapp: <title>". Its message follows the app's build stage (detecting game → setting up wrapp → copying installer → installing → configuring → saving). The app's own log lines stream underneath as a collapsible step. |
| `wrapp update` | "Build Second Chance", "Update template", "Re-sign" |
| `test unit` | "Build for testing", then the unit live region (see "Live regions"). |
| `test integration` | "Build for testing", then the integration live region (see "Live regions"). |
| `release` | Each phase is a step: preflight, version, project, changelog, unit tests, Release build, package. |
| `--on <host>` | "Sync to <host>" (rsync), then the remote's own Noora output over `ssh -t`, then "Fetch report". |
| `clean` | A progress step for each target. |

**Live regions (several Noora components on screen at once).** `UI/StackedRenderer.swift`
is about 100 lines.
- **How it works.** It owns one region of the terminal and hands out ordered `Slot`s.
  Each slot conforms to Noora's `Rendering`, and each component is given its own
  slot as `renderer:`. A slot's `render` stores that component's latest frame. The
  stack then erases the whole region and redraws every slot's frame in order.
- **Threading and throttling.** A lock serialises redraws, and they're capped at
  about 15 fps.
- **Permanent lines.** Lines that should stay, such as a finished test's ✓/✗ line or
  a collapsed step, are printed *above* the region and scroll away normally.
- **Height.** The region is kept within the terminal height, re-read on `SIGWINCH`,
  by trimming the table first, showing running and failed rows and then the most
  recent ones.
- **When it isn't used.** It only applies in interactive `collapsed` mode. In `full`
  or `raw` mode, or when not interactive, live components are skipped and each event
  prints as a plain line instead. The final table is still printed once at the end.

**Test runs use it.**
- **Unit, two slots:**
  - A **progress bar** for the whole run: "47/212 · 2 failed · LogStoreTests/drain…".
    The total comes from `xcodebuild test-without-building -enumerate-tests
    -test-enumeration-format json` (available in this Xcode), run before the tests.
  - Below it, an **updating table** with one row per suite: pending, running,
    passed, failed or skipped counts, and duration.
  - Per-test start and finish events are parsed from xcodebuild's raw output (Swift
    Testing's `◇ Test … started` / `✔ … passed` / `✘ … failed` lines) before the
    output goes to xcbeautify and the log file.
- **Integration, three slots:**
  - A **progress bar** of games done out of the total.
  - A **progress step** for the current game's stage: "haunted-carousel: installing
    game (disk 1 of 2)", then "launching (WrappPuppeteer)", then "quitting".
  - An **updating table** of every game: pending, running, passed, failed or
    permission, engine and duration.
  - The stage comes from the same JSON-lines progress stream as `wrapp build`.
    `DiskInstallIntegrationTests` writes to it when `TEST_RUNNER_PROGRESS_PATH` is
    set. Its existing `RecordingEventSubscriber` sits beside a shared
    `ProgressFileWriter`, which also covers the launch and quit phases.
- **Bare `sc test`.** The unit region, then the integration region. Each one
  collapses to its final table when it finishes.
- **`wrapp build`.** Two slots: the stage progress step, with the collapsible log
  tail underneath.

**Change your mind mid-build: launch when done.**
- **The key.** While a wrapp build runs in an interactive terminal, the live region
  has a footer slot: `l  launch when done: off`. Pressing `l` toggles it.
  - It starts **off** for `wrapp build`.
  - It starts **on** for `wrapp run` when that does a wrapp build (missing wrapp, or
    `--refresh-wrapp full|template`), so `l` there means "actually, don't launch".
- **Launching.** On a successful build with the toggle on, the command does exactly
  what `wrapp run` does next: it `exec`s the wrapp with stdio attached.
  - From `wrapp build`, the wrapp launches with the defaults, because that command's
    `--debug` set controls the build, not the launch. The footer says so:
    `launch when done: on (defaults)`.
  - From `wrapp run`, the launch uses that command's own `--debug` values and `--` args.
  - On a failed build, the toggle is ignored and the error is shown.
- **Implementation.** Keys are read with Noora's `KeyStrokeListener` utility, which
  sets raw mode. Noora restores the terminal on SIGINT and SIGTERM, and the UI also
  restores it on every exit path. The footer is just another `StackedRenderer` slot.
- **The headless app's stdin is `/dev/null`**, so it can never swallow keystrokes.
- **No terminal, no toggle.** When stdin isn't a TTY (piped, CI, or `--on` without
  a terminal), the footer isn't shown and the launch choice is whatever the command
  and flags said.
- **Over the GUI-session re-run and `--on`.**
  - `--on` uses `ssh -t`, so keys pass straight through.
  - The GUI-session re-run currently feeds its pty from `tail -f /dev/null`. The port
    replaces that with a FIFO. The outer process puts its own TTY into raw mode and
    copies stdin into the FIFO, so the toggle works there too.
  - If the FIFO forwarding can't be made reliable, the footer is hidden in a re-run
    rather than shown and ignored.

**Wrapp build progress needs a small app change.** Headless runs only log free text
today. `CLIBuilder` would subscribe to the bus's `.progress(WrappBuildState)` events
and, when `SECOND_CHANCE_PROGRESS_PATH` is set, append one JSON line per state change
to that file. The CLI tails the file. This uses the events contract that already
exists, keeps logs and progress separate, and doesn't affect GUI runs. It is
documented in `docs/wrapp-build.md`.

**Tables** (static):
- **Test results.** Read from the `.xcresult` with `xcrun xcresulttool get
  test-results summary/tests --format json`, showing suite, passed, failed, skipped
  and duration.
- **Integration per-game results.** Game, engine, result and duration, plus the
  WrappPuppeteer outcome when it ran. A code 3–5 shows as "permission" rather than
  "failed", with a pointer to the TCC section of testing.md.
- **`release`.** Version, build number, zip, size, architectures and sha256.
- **`clean`.** What was removed and the space freed.

**Alerts:**
- A **success** alert ends each command with its key result. For example: the wrapp
  path; for tests, an HTML report link when the report wasn't opened; for release,
  the publish commands as next steps.
- **Warnings**: not on `main`, missing commit hook, non-conventional commits, a
  locked screen on commands that don't need the screen, and the release not being
  notarised.
- **Errors** say what to do next. For example, an unknown slug lists the slugs that
  have installers, a missing wrapp suggests `sc wrapp build <slug>`, and a missing
  tool gives the `brew install …` command.

**Prompts** (TTY only, and each has a flag):
- `sc wrapp build|run` with no slug offers a **single choice** of the games that have
  installers. `wrapp run` shows only games that already have a wrapp, unless it's
  told to build one.
- `sc clean` with no target offers a **multiple choice** with the size of each.
  Deleting asks a **yes/no** first, which `--yes` skips.
- `sc test integration` with no slugs runs everything, as before. Picking games is
  left to the arguments.

**HTML report: `--open-report failures|always|never`.** The terminal table now covers
a passing run, so by default the HTML report only opens when something failed.

## Implementation

**Layout.** A Swift package `Tools/sc/` with an `sc` executable target (just `@main`),
an `SCKit` library target and an `SCKitTests` test target. `SCKit` is organised as:
- `Commands/`: `SC.swift` (root and global options), `App.swift`, `Wrapp.swift`,
  `Test.swift`, `Release.swift`, `Setup.swift`, `Clean.swift`, `InGUISession.swift`.
- `Support/`:
  - `Repo.swift`: repo root from `SC_REPO_ROOT`, else walk up to `SecondChance.xcodeproj`.
  - `Xcode.swift`: the only xcodebuild call site. Always `ONLY_ACTIVE_ARCH=NO`;
    output goes through xcbeautify into the UI's step, according to `--logs`.
  - `UI/UI.swift`: the Noora wrapper (steps, tables, alerts, prompts, log-file teeing),
    built with our resolved `Terminal`.
  - `UI/StackedRenderer.swift`: the live region of slots, unit-tested by rendering
    into a recording `StandardPipelining` and checking the erase/redraw sequence.
  - `TestProgress.swift`: parses Swift Testing's per-test lines, the
    `-enumerate-tests` JSON and the progress JSON-lines stream into events.
  - `TestResults.swift`: reads `xcresulttool` JSON into the result tables.
  - `Processes.swift`: wrappers over swift-subprocess (streaming, xcbeautify piping,
    teardown) and `execv` for runs that keep the terminal.
  - `GUISession.swift`, `Remote.swift`.
  - `DebugOptions.swift`: the mapping table.
  - `WrappSource.swift`.
  - `ProjectVersion.swift`: a port of the awk pbxproj rewrite, keeping the "exactly
    4 + 4 rewrites" guard.
  - `Changelog.swift`.
- `GameCatalog/`: symlinks to `SecondChance/Models/GameInfo.swift` and
  `SecondChance/Services/GameInfoProvider.swift`. Both are Foundation-only, so slug
  → title → `Nancy Drew - <title>.app` uses the real catalog.
- `Tests/SCKitTests/`: Swift Testing for the pure parts. These are the pbxproj rewrite
  (against a fixture copy of the real project), changelog insertion, debug-option
  parsing/validation and → env/args, source → env, and argument forwarding for `--on`.
  Also `SC.parseAsRoot` cases for every command: option conflicts, `--` pass-through,
  bare `sc test` resolving to all, and invalid enum values being rejected.

**`./sc` shim at the repo root.** I chose a package plus shim over a single
`#!/usr/bin/env swift` script for four reasons:
1. A script can't compile `GameInfoProvider.swift` alongside itself, which would bring back text parsing.
2. A script can't import swift-argument-parser.
3. A script recompiles on every run, which takes seconds at this size.
4. A script has no test target.

The shim is about 5 lines with no logic. It runs
`swift build -c release --package-path Tools/sc` quietly (it prints only on
failure), then `exec`s the binary with `SC_REPO_ROOT` set.

## Verification
- `swift test --package-path Tools/sc`: tool unit tests.
- `./sc test unit`: passes, runs the 9 existing suites plus SecondChanceTests,
  and skips integration and exiftool. Compare the suite list with the old allowlist.
- `./sc app build` from a subdirectory collapses to one ✓ line, with the log in `DerivedData/sc-logs/`.
- Break the build deliberately: the step expands and shows the compiler error and log path.
- `./sc app build | cat` defaults to raw: the unformatted xcodebuild output, with no
  colour or animation. `NO_COLOR=1 ./sc app build` in a terminal stays collapsed but
  uncoloured. `--logs full` matches today's default output, and `--logs raw` matches
  today's `--raw-logs`.

  output is still raw. That checks the resolved mode is forwarded rather than detected again under the pty.

  - The progress bar and the suite table update together without tearing.
  - Resizing the window keeps the region within the screen.
  - The bar's total matches the `-enumerate-tests` count.

  `./sc test unit | cat` prints plain per-test lines and a final table instead.

  the game table together.
